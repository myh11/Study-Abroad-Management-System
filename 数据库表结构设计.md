+ `AGENT`

# 四、字段定义说明（重点字段）

## 1）`applications.current_status`

这是全系统最关键字段，只允许通过你定义好的状态型接口修改。
因为 PRD 的状态流转、撤销规则、候补、调剂、归档都是围绕申请状态来的。

## 2）`applications.source_application_id`

用于调剂派生申请。
PRD 明确要求接受调剂时生成新申请，并保留来源申请编号。

## 3）`applications.waitlist_confirm_deadline`

这是为了支撑“候补补位后 48 小时确认”的规则。
PRD 明确要求超时视为放弃并转给下一位。

## 4）`rule_snapshots.*`

提交申请时写入。
它不是“当前规则”，而是“申请提交当时的规则副本”，避免管理员后续改门槛或配额影响历史申请。

## 5）`school_quotas` / `major_quotas`

这是我对 PRD 的工程化拆分。
PRD 里学校表、专业表都写了总名额/已用/剩余，但真正实现并发占位时，更稳的是单独维护批次配额表。PRD 也明确要求占位时锁定学校配额记录和专业配额记录，并整体事务回滚。

## 6）`waitlist_records`

PRD 虽然没有单独列这个表，但候补排序、补位、超时、批次失效都是完整子流程；单独拉表会比全塞到 `applications` 里清晰很多，也更适合你单独负责候补逻辑。依据候补排序、48 小时确认、批次失效规则，这样拆更稳。

# 八、开工前冻结项

这份 SQL 草案开工前冻结 2 项：

第一，**不保留“国内审核通过”这个持久化状态**。
统一按接口文档执行：国内审核通过后自动进入 `SCHOOL_REVIEWING`。

第二，文件存储方案统一如下：

- 开发阶段采用本地文件存储
- 数据库必须新增 `files` 表保存文件元数据
- `transcripts.file_id`、补件附件等统一关联 `files.id`
- 文件访问必须经过后端鉴权，不直接暴露真实存储路径

然后在 SQL 里新增一个 `files` 表，例如：

```c
CREATE TABLE files (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '文件编号',
  file_key VARCHAR(100) NOT NULL COMMENT '文件唯一标识',
  original_name VARCHAR(255) NOT NULL COMMENT '原始文件名',
  storage_path VARCHAR(500) NOT NULL COMMENT '存储路径',
  file_type VARCHAR(50) NOT NULL COMMENT '文件类型',
  file_size BIGINT NOT NULL COMMENT '文件大小',
  business_type VARCHAR(50) NULL COMMENT '业务类型 transcript/attachment',
  uploaded_by BIGINT NULL COMMENT '上传人',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_file_key (file_key),
  CONSTRAINT fk_file_user FOREIGN KEY (uploaded_by) REFERENCES users(id)
) COMMENT='文件表';
```

# 二、按业务理解表关系

## 1. 用户和角色关系

`users` 是所有角色共用表：

+ 代理专员
+ 国内审查员
+ 学校专员
+ 管理员

它和很多业务表关联，因为：

+ 谁创建了批次
+ 谁创建了申请
+ 谁做了国内审核
+ 谁做了学校审核
+ 谁触发了状态变更
+ 谁写了审计日志

这和 PRD 的角色模型、权限矩阵是一致的。

------

## 2. 批次是很多业务的“总线”

`admission_batches` 会关联：

+ 学校配额
+ 专业配额
+ 申请
+ 规则快照
+ 候补记录

因为 PRD 明确要求：
所有申请、配额、候补、审核都必须绑定一个招生批次。

------

## 3. 学校、专业、配额关系

### 基础配置

+ `schools`
+ `majors`

### 运行时配额

+ `school_quotas`
+ `major_quotas`

这里我故意拆成两层，是为了避免冲突：

+ 基础表负责“规则配置”
+ quota 表负责“运行时名额变化”

因为 PRD 明确要求学校总名额与专业名额双重控制，并且占位时要锁定学校配额和专业配额记录。

------

## 4. 学生资料链

一个申请会依赖三类资料：

+ `students`
+ `transcripts`
+ `personal_statements`

再由 `applications` 引用它们。

也就是：

```text
学生主档 + 成绩单 + 自荐材料 -> 组成申请
```

这和 PRD 的学生表、成绩表、自荐材料表、申请表模型一致。

------

## 5. 申请是系统核心主表

`applications` 是全系统中心。

它连出去的表最多：

+ 规则快照
+ 国内审核
+ 学校审核
+ 候补记录
+ 状态历史
+ 调剂来源（自关联）

也就是说：
**任何真正的业务流转，最后都得落到 applications。**

------

## 6. 候补与补位是独立子流程

`waitlist_records` 单独存在，不塞进 `applications`，这样更清晰：

+ 排名
+ 排序原因
+ 候补状态
+ 补位时间
+ 确认截止时间
+ 失效时间

因为 PRD 对候补机制定义得非常完整：排序规则、48 小时确认、批次结束自动失效。

------

## 7. 历史与审计是两套日志

### `application_status_histories`

记录状态变化链路：

+ 旧状态
+ 新状态
+ 谁触发
+ 什么动作触发

### `audit_logs`

记录关键操作审计：

+ 操作人
+ 实体
+ 操作类型
+ 新旧值

PRD 要求这两类都要保留。

# 八、你现在最适合怎么用这份东西

## 主文档

1. 接口文档

4. **附录A：数据库表关系图**

这样最清楚。

# 九、最后一句话总结

这份“表关系图 + 接口读写表映射”本质上就是：

**把“哪个接口动哪几张表”彻底讲清楚。**

这样你们三个人开发时：

+ A 不会乱碰审核和状态核心
+ B 不会乱碰学校审核和配额
+ 你 merge PR 时能一眼看出有没有越界

而且整套映射和 PRD 的角色权限、状态机、候补、调剂、配额控制、日志追踪要求是对齐的。
