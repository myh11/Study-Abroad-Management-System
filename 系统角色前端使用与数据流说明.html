系统里有哪些角色

前端不是所有人都看同一套页面。登录成功后，系统会根据账号角色分配可见菜单、工作台指标和可执行动作。

管理员 Admin

负责基础数据配置和全局查看，包括批次、学校、专业、用户、配额、日志等后台页面。

Dashboard 批次管理 学校/专业 用户/配额 审计日志

代理专员 Agent

负责创建申请、保存草稿、提交申请、补件、候补确认、调剂处理，是申请流的起点。

申请列表 创建申请 详情页 补件 候补确认

国内审核员 Domestic Reviewer

负责认领申请并做国内初审，判断材料、身份、基础成绩和风险等级。

审核列表 申请详情 认领审核 提交结论

学校专员 School Reviewer

负责学校侧终审，结合门槛、配额、学术分与匹配度给出录取、候补、调剂或拒绝。

学校审核列表 学校详情 学校评分 学校决策

系统里流动的核心数据

一条申请不是只有“一个表单”。从前端视角看，它至少由用户信息、申请主体、审核结果、候补记录、状态历史几类数据共同组成。

认证与权限数据

  • users：username、role、schoolCode、mustChangePassword
  • token：登录后写入请求头，决定后续接口权限
  • /api/auth/me：前端刷新后恢复当前登录态

申请主体数据

  • applications：applicationId、batchId、targetSchoolCode、targetMajorCode、currentStatus
  • students：姓名、性别、出生日期、学校、年级、联系方式、证件号
  • transcripts / scores：各学科成绩、均分、挂科数、成绩单附件
  • personal statement：个人陈述

审核与过程数据

  • domestic_reviews：材料完整性、身份匹配、成绩达标、风险等级、结论、备注
  • school_reviews：门槛判断、配额判断、学术分、材料分、匹配分、总分、学校结论
  • waitlist_records：候补状态、确认截止时间
  • status_histories / audit_logs：状态变化和操作轨迹

申请状态是怎样推进的

前端每个按钮本质上都在请求“把申请从一个状态推进到另一个状态”。只要理解状态流，就能理解为什么有些按钮能点、有些会报错。

01

DRAFT

代理专员创建或保存草稿后进入此状态。

  • 可编辑
  • 可提交
  • 调剂新草稿也属于此状态
02

SUBMITTED

代理正式提交后进入国内审核池。

  • 国内审核员可认领
  • 不可再按草稿编辑
03

DOMESTIC_REVIEWING

已被国内审核员认领，等待审核结论。

  • 可通过
  • 可要求补件
  • 可国内拒绝
04

SCHOOL_REVIEWING

国内审核通过后转入学校审核。

  • 可录取
  • 可候补
  • 可建议调剂
  • 可学校拒绝
05

WAITLIST / RESERVED

学校录取后进入 RESERVED，候补则进入 WAITLISTED 再等待确认。

  • 候补可被推进到待确认
  • 待确认后可接受或关闭
06

CLOSED

被拒绝、被取消、候补关闭或原申请被调剂关闭后都会落到终态。

  • 终态不可再继续推进
  • 保留历史记录和审计日志

随着操作，数据如何流动

下面用“前端页面 -> 接口 -> 后端持久化 -> 状态/权限返回”的方式看一条申请怎么被创建、审核和收尾。

1. 登录与身份建立
登录页提交 username、password 到 /api/auth/login
后端返回token、userId、role、schoolCode、mustChangePassword
前端保存token 写入请求头，currentUser 写入状态管理
2. 代理创建申请
创建页学生信息、成绩信息、个人陈述、批次、学校、专业
草稿入库applications + students + 成绩/附件 + 个人陈述
状态DRAFT，可继续编辑，也可正式提交
3. 国内审核
认领POST /api/domesticreviews/{id}/claim，仅 SUBMITTED 可认领
提交结论materialComplete、identityMatched、basicScorePassed、authenticityRiskLevel、standardizationPassed、result、comment
结果PASS -> SCHOOL_REVIEWING；SUPPLEMENT_REQUIRED -> DOMESTIC_SUPPLEMENT；REJECT -> DOMESTIC_REJECTED
4. 学校审核
学校评分academic_score、material_score、matching_score、total_score
规则判断school_threshold_passed、major_threshold_passed、school_quota_passed、major_quota_passed
结果RESERVE、WAITLIST、SUGGEST_ADJUSTMENT、REJECT
5. 候补 / 调剂 / 终态
候补WAITLISTED -> promote -> WAITLIST_PENDING_CONFIRM -> 接受后 RESERVED，拒绝后 CLOSED
调剂原申请会被关闭，新调剂申请生成 DRAFT，再回到代理提交流程
终态沉淀statusHistory、auditLogs 持续累积，供前端详情页追溯

每个角色在前端上如何使用

点击不同角色，可以看到它在前端的典型路径、使用页面、请求的数据、以及每一步的判定结果。

管理员前端使用路径

  1. 登录页输入管理员账号，若首次登录则先改密。
  2. 进入 Dashboard，查看全局申请、用户、候补、批次指标。
  3. 进入批次、学校、专业、用户、配额页面维护基础数据。
  4. 进入审计日志与状态历史页面排查业务流转。
登录：/api/auth/login 工作台：/api/dashboard/summary 配置：/api/batches / schools / majors / users / quotas

管理员的数据作用

管理员通常不直接推进单条申请状态，但会决定所有后续流程的“边界条件”。例如批次是否启用、学校专业是否存在、配额是否足够，都会影响学校审核能否通过。

批次是否开放 学校/专业合法性 用户角色与权限 配额约束

代理专员前端使用路径

  1. 登录后先看 Dashboard，确认本人草稿数、补件数、候补待确认数。
  2. 进入申请列表页查看自己的申请，按状态筛选。
  3. 进入创建页填写学生信息、成绩、个人陈述、目标学校和目标专业，先保存草稿。
  4. 在详情页检查信息，执行提交申请。
  5. 若国内审核要求补件，则再次进入详情页补充后重提。
  6. 若进入候补待确认，则执行接受/放弃；若收到调剂草稿，则继续修改并重新提交。
列表：GET /api/applications/my 详情：GET /api/applications/{id} 提交：POST /api/applications/{id}/submit 候补确认：POST /api/applications/{id}/waitlist-confirm

国内审核员前端使用路径

  1. 登录后看 Dashboard，了解待认领、审核中、补件中、拒绝数量。
  2. 进入国内审核列表页，查看真实审核池。
  3. 打开某条详情，先确认当前状态是不是 SUBMITTED。
  4. 执行认领，状态变为 DOMESTIC_REVIEWING。
  5. 填写审核表单并提交，决定进入学校审核、补件或国内拒绝。
列表：GET /api/domesticreviews 认领：POST /api/domesticreviews/{id}/claim 提交：POST /api/domesticreviews/{id}/submit

国内审核提交的数据

materialComplete identityMatched basicScorePassed authenticityRiskLevel standardizationPassed result: PASS / SUPPLEMENT_REQUIRED / REJECT comment

学校专员前端使用路径

  1. 登录后先看本校工作台指标，只看到本校目标申请。
  2. 进入学校审核列表页，查看本校学校审核池。
  3. 打开详情，核对学生、学校、专业、历史状态和前置审核摘要。
  4. 填写分项评分与结论，提交学校审核。
  5. 如果给出候补，后续由候补流程继续推进；如果建议调剂，会生成新的调剂草稿。
列表：GET /api/school-reviews 详情：GET /api/applications/{id} 提交：POST /api/school-reviews/{id}/submit

每一步怎么判断“通过”还是进入什么状态

这部分是最适合讲给老师听的。因为前端看到的不是“随便一个按钮”，而是基于权限、当前状态、表单数据共同决定是否可执行。

登录 提交 username + password 到 /api/auth/login。如果成功，返回 token 和角色；如果 mustChangePassword = true，前端必须先走改密页，未改密时业务接口会被拦截。
保存草稿 只要代理提交了基础表单数据，后端会将申请保存为 DRAFT。此时主要目标是把申请结构建立起来，并记录学生、成绩、个人陈述、目标学校与专业。
正式提交申请 只有 DRAFT 或 DOMESTIC_SUPPLEMENT 状态可以重新提交。提交成功后变为 SUBMITTED，表示进入国内审核池。
国内审核认领 只有当前状态是 SUBMITTED 时，国内审核员才能调用认领接口。认领成功后变为 DOMESTIC_REVIEWING。
国内审核提交 只有 DOMESTIC_REVIEWING 可提交。
result = PASS -> SCHOOL_REVIEWING
result = SUPPLEMENT_REQUIRED -> DOMESTIC_SUPPLEMENT
result = REJECT -> DOMESTIC_REJECTED
学校审核提交 只有 SCHOOL_REVIEWING 可提交。
RESERVE -> RESERVED
WAITLIST -> WAITLISTED
SUGGEST_ADJUSTMENT -> 原申请先进入 ADJUSTMENT_SUGGESTED，随后原申请关闭，并生成新的调剂草稿 DRAFT
REJECT -> SCHOOL_REJECTED
候补推进 只有 WAITLISTED 才能被推进为 WAITLIST_PENDING_CONFIRM。这一步会生成候补确认期限等信息。
候补确认 只有 WAITLIST_PENDING_CONFIRM 才能确认。
接受 -> RESERVED
拒绝 / 失效 -> CLOSED
调剂处理 “接受调剂”并不是对原申请直接点。它只能作用在学校建议调剂后生成的“新调剂草稿”上。这个草稿本身必须是 DRAFT 且带 sourceApplicationId，接受后重新进入 SUBMITTED。
终态 DOMESTIC_REJECTED、SCHOOL_REJECTED、候补拒绝、取消、原申请被调剂关闭等情形最终都会沉淀为 CLOSED 或终止性状态，前端仍可查看历史，但不再继续推进。
蓝色：常规进行中状态
绿色：通过或录取类结果
黄色：待补件、候补、待确认类中间状态
红色：拒绝或关闭类终止状态

口头汇报时可以用一句话概括：前端并不是简单展示表单，而是在不同角色下，把申请、审核、候补、调剂等数据对象按状态驱动的方式串成一条完整业务链。
